# RFC 0023: Structured permissions

- Created: 2026-08-29T10:31:32-05:00
- Current implementation: [Implementation and gaps](CURRENT.md)

## Summary

Permissions v2 separates package declarations, system installation policy, and per-user grants. Structured prototxt records and capability-scope propagation replace legacy string permissions.

## Design overview

Permissions v2 separates static package declarations, system installation
policy, and per-user runtime grants. The current implementation intentionally
breaks the legacy string-permission manifest format: app manifests now declare
structured permission records in prototxt.

## Manifest Schema

App manifests use `bexos.app.Manifest` from `idl/bexos/app/manifest.proto`.
Package-level and process-level permissions are both structured declarations:

```protobuf
enum PermissionRequirement {
  PERMISSION_REQUIRED = 0;
  PERMISSION_OPTIONAL = 1;
}

message PermissionDeclaration {
  string name = 1;
  repeated string values = 2;
  PermissionRequirement requirement = 3;
  string usage_description = 4;
}

message Manifest {
  repeated PermissionDeclaration permissions = 4;
}

message Process {
  repeated PermissionDeclaration permissions = 3;
}
```

Example prototxt:

```protobuf
permissions {
  name: "CAMERA"
  values: "front"
  values: "back"
  usage_description: "Display camera previews."
}
permissions {
  name: "RAW_SENSOR_TUNING"
  values: "sensor0"
  requirement: PERMISSION_OPTIONAL
  usage_description: "Tune raw camera sensor controls."
}
```

An empty `values` list means the permission has no narrower resource scope.
When values are present, every runtime request for that permission must name an
exact subset of the declared values.

## Permission Stores

`//lib/permission_store` owns the shared permission-store model:

- `SystemGrantRecord { package_id, permission_name, allowed_values, verified_at }`
- `UserGrantRecord { uid, package_id, permission_name, state, granted_values }`
- `MemoryPermissionStore` for no-std appd and tests.
- `persistent::PermissionStoreDb` behind `std + redb_backend` for host/block
  backed system and user grant tables.

The implemented persistent layout is:

- system declarations and UID 0 grants under
  `/data/system/bexos.platform.appd/permissions.redb`;
- nonzero UID grants under `/data/users/<uid>/permissions.redb`, opened through
  `VfsManager.GetUserHomeDirectory` so they only exist inside the mounted
  encrypted user image.

The current guest appd path wires the memory store into boot, install,
uninstall, launch, and optional permission requests. System-store
reconciliation scrubs legacy nonzero-UID rows; user-store reconciliation removes
records for uninstalled packages or declarations that no longer exist. Locked
nonzero users cannot launch or request permission, and user lock/delete events
purge cached grants and revoke live per-user capability routes.

## Lifecycle

At install/import time, appd records declared package permissions into
the system grant store after the package manifest has been accepted.

At launch time, appd combines package-level and selected process-level
permission declarations, then auto-grants every `REQUIRED` declaration for the
launching UID. This is the current v1 behavior because trusted consent UI is
not wired into appd yet. Once consent UI exists, this step should prompt
for required grants and deny launch when the user rejects one.

For optional permissions, `bexos.app.lifecycle.AppLifecycleControl` exposes:

```fidl
type PermissionState = strict enum : uint8 {
    GRANTED = 1;
    DENIED = 2;
    RESTRICTED = 3;
};

8: RequestPermission(struct {
    package_id string:128;
    process_name string:64;
    uid uint64;
    permission_name string:128;
    service_name string:128;
    capability string:128;
    requested_values vector<string:128>:16;
}) -> (resource struct {
    status AppLifecycleStatus;
    state PermissionState;
    granted_values vector<string:128>:16;
    granted_handle handle:OPTIONAL;
});
```

App-service grants the request only when the permission is declared as
`PERMISSION_OPTIONAL`, the requested values are an exact subset of that
declaration, the selected consumed service and capability are declared with
explicit methods, and the selector resolves to one provider whose capability
permission annotation scopes to the requested permission. Undeclared permission
names or locked users return `ACCESS_DENIED`, ambiguous selectors return
`INVALID_ARGS`, unavailable providers return `NOT_FOUND`, and durable-store
failures return `STORAGE`.

## Capability Scope Propagation

The service broker still filters FIDL capability groups using the permission
metadata generated by `fidlc`. When it mints a `BoundCapability`, it also
attaches the granted values for that capability's permission.

Consumers can now narrow service access in their own manifests:

```protobuf
message ConsumedService {
  string name = 1;
  LinkType link_type = 2;
  string filter = 3;
  repeated ConsumedCapability capabilities = 4;
}

message ConsumedCapability {
  string capability = 1;
  repeated MethodDependency methods = 2;
}

message MethodDependency {
  uint64 ordinal = 1;
  LinkType link_type = 2;
}
```

An empty `capabilities` list preserves compatibility and requests every
provider capability allowed by visibility and permission policy, but method
access is explicit: an empty consumed method list requests no methods and does
not create an endpoint for that capability. Required method dependencies must be
exposed by the provider or binding fails. Optional method dependencies are
included only when the provider exposes them.

Startup service grants and provider binding notifications now include those
permission values in the descriptor:

```text
service|protocol|capability|ordinal,ordinal|value,value
```

Apps hosting services receive the provider endpoint together with this metadata
and can inspect the granted resource scope before serving requests.

Optional `RequestPermission` calls also return a live client endpoint in
`granted_handle`. Appd retains the original provider endpoint, delivers
duplicates to the current provider manager, keeps the client channel valid
through provider crashes, and replays a duplicate retained endpoint when the
same compatible provider is republished. Incompatible replacement capabilities
or permanent provider removal close the route.
