# RFC 0051: Trusty security stack

- Created: 2026-09-02T20:48:09-05:00
- Current implementation: [Implementation and gaps](CURRENT.md)

## Summary

Trusty provides independent security services behind explicit transport, storage, and authorization boundaries. The orchestrator remains limited to core lifecycle and heart-transplant coordination; physical-board and production requirements remain explicit.

## Design overview

The standalone x86 development build and its validation are documented in [current x86_64 support](../../x86_64-support.md). It does not satisfy integrated BexOS transport, isolated x86 execution, production provisioning, or the heart-transplant requirements described here.

The repository has an integrated x86 EFI/SVM Trusty product as well as a
standalone development build; see [current x86 support](../../x86_64-support.md).
The [completion checkpoint](../../trusty-completion.md) separates implemented
replacement foundations from the remaining ARM/x86 live Trusty work. Standalone
execution alone does not establish the isolation or update guarantees below.
The [approved live-replacement design](../../design/trusty-live-replacement.md)
specifies the permanent owners, TA continuity, durable recovery and required
completion gates.

## Status and scope

BexOS uses the pinned upstream Trusty revision for its QEMU ARM64 secure-world image. The image includes upstream storage, KeyMint, Gatekeeper, AVB, and AuthMgr FE/BE, plus the BexOS orchestrator TA. The orchestrator is retained solely for Trusty core/update lifecycle and heart-transplant coordination; it is not a general security-service gateway.

The implementation targets QEMU and board-neutral, fail-closed contracts. It does not claim physical-board validation. A board without an authenticated BL33 loader, provisioned root of trust, Trusty IPC transport, and RPMB support must report the missing capability and refuse dependent operations.

## Boundaries

```text
privileged BexOS clients
  keychaind  usersd  boot verifier  updated
               │ typed, capability-restricted requests
               ▼
             teed ── Trusty driver (SMC/shared memory; virtio-TIPC contract)
               │
               ▼
Trusty: KeyMint | Gatekeeper | storage | AVB | AuthMgr FE/BE | orchestrator
               │
               ▼
       RPMB (or QEMU's development RPMB proxy/image)
```

Only `teed` owns raw driver access. It keeps provider-neutral transport and session state and migrates that state during a heart transplant. Failed, interrupted, or malformed calls are explicit failures that clients may retry; there is no fallback from a real Trusty product to the software provider. Ordinary applications never receive a raw TEE capability.

The Trusty driver exposes session open, invoke, close, reset, and typed application discovery. Its QEMU implementation is a transport-compatible test backend. Hardware implementations fail closed when their SMC/shared-memory, virtio-TIPC, root-of-trust, or RPMB contracts cannot be established.

## Service roles

| Trusty application | BexOS use |
| --- | --- |
| KeyMint | Authoritative hardware key generation, signing, AES-GCM, HMAC, opaque blobs, and secret-envelope encryption. |
| Gatekeeper | Password enrollment, verification, throttling, secure user IDs, and hardware-authentication tokens. |
| storage | Persistent state for KeyMint, Gatekeeper, AVB, and AuthMgr through authenticated RPMB I/O. |
| AVB | Device lock state, rollback indexes, and verified-boot decisions used before kernel entry. |
| AuthMgr FE/BE | Upstream DICE and secure-service connection authorization. It is not a Gatekeeper-token broker. |
| BexOS orchestrator | Trusty core update/lifecycle and supported secure-world handovers only. |

Gatekeeper and KeyMint share the secure secret that validates authorization. Gatekeeper tokens travel directly from `usersd` to KeyMint with the requested operation. AuthMgr is not in that token path.

## User authentication and encrypted filesystems

`usersd` owns password enrollment and verification. A successful create flow enrolls Gatekeeper, creates an auth-bound KeyMint HMAC-SHA256 blob, verifies the password, initializes BexFS, then locks it. Any failed stage rolls back the Gatekeeper record, KeyMint material, filesystem, and user record.

For an unlock, `usersd` verifies the password with Gatekeeper and derives the 32-byte filesystem UKEK through authenticated KeyMint HMAC over `bexos.ukek.v1\0 || uid_le64`. The UKEK is passed once to `vfsd`, then zeroized. It is never persisted or generated by the host. Existing software-only secret records remain readable, but new hardware keys are KeyMint opaque blobs; `keychaind` stores aliases, characteristics, public material, opaque blobs, and encrypted secret payloads, never private key material.

`usersd` caches successful hardware-authentication tokens for five minutes. Lock, disable, deletion, password replacement, and expiry invalidate them. Unlocking an already-unlocked user reauthenticates and refreshes the token without reopening the filesystem. `keychaind` asks the private usersd broker for a token on every `REQUIRE_USER_AUTH` operation and returns `ERR_LOCKED` when none is current; it has no second cache.

During a usersd heart transplant, valid cached tokens are carried by kernel-controlled handover state with their original secure timestamp and expiry. Migration never extends their lifetime. The source state is retained after an aborted handover and cleared only after commit.

## Storage and board contracts

Trusty storage treats the host storage path as untrusted transport. QEMU uses a development-only RPMB proxy and persistent `rpmb0` image owned by the QEMU lifecycle; starting an instance creates or attaches the proxy, a restart uses the same image, and all child processes are terminated when QEMU exits. Tests exercise persistence across boots and fail closed on corrupted authenticated state. QEMU keys and its RPMB image are not production provisioning.

Future eMMC and UFS boards must provision a unique RPMB authentication key, restrict frame transport to the secure-world proxy, provide durable atomic authenticated writes and monotonic read counters, reserve Trusty shared memory, expose only the documented SMC/TIPC doorbell, provision the verified-boot root, and authenticate the BL33 verifier through TF-A.

## Verified boot

TF-A authenticates a small BL33 verifier. The verifier consumes standard libavb-compatible vbmeta, asks the Trusty AVB TA to enforce device lock state and rollback indexes, verifies the kernel, BootFS, and platform-policy hashes, then locks the boot result and enters the kernel. Bazel produces signed vbmeta and all QEMU boot artifacts using the explicit development root key.

The kernel consumes only the versioned handoff produced by that verifier. It does not manufacture secure-boot evidence and must not accept a secure-boot or RPMB flag unless the corresponding verified backend was active. Modified kernel, BootFS, policy, vbmeta, rollback, lock-state, and unauthenticated-verifier cases are required negative tests.

## Build, lifecycle, and tests

The Trusty superproject remains pinned. Its dependency closure is expanded only for the listed applications, and Bazel builds firmware, generated protocol code, and boot artifacts; generated outputs are not checked in. Trusty core updates retain the orchestrator state model and verify that the orchestrator remains reachable after upstream applications are added and after supported handovers.

The intended test suite covers typed-client framing and malformed responses,
driver session lifecycle, usersd/keychaind/teed migration, Gatekeeper user flows
and token expiry, KeyMint algorithms and opaque-blob persistence, AuthMgr
acceptance/rejection, AVB verification negatives, RPMB multi-boot persistence
and corruption, and orchestrator update behavior.

### Current implementation checkpoint

As of 2026-09-09, live Trusty replacement remains incomplete on both QEMU
products. Architecture-bound slot/selection support, a shared live coordinator
and writer gate, protected codecs, capability queries, and a source-built ARM
secure transition platform are being implemented. They do not establish actual
TA migration, candidate execution, retained-client cutover or product acceptance.
See the [current checkpoint](../../trusty-completion.md) for exact status.

### Historical implementation checkpoint — 2026-09-04

As of 2026-09-04, the signed firmware builds and contains the complete seven-TA
set. Host-focused AVB, vbmeta, typed-client, driver, teed, usersd, keychaind,
debugd, and QEMU-runner tests passed before the final AuthMgr/logger and usersd
migration edits. A QEMU run verified TF-A authentication, BL33 partition
verification, and enumeration of every required TA, but failed in AuthMgr FE
startup before normal-world userspace. A logger-safe follow-up firmware image
builds, but was not boot-tested because execution was stopped at that point.

This is not a completed E2E implementation claim. In particular, the final
QEMU multi-boot/tamper suite, final focused tests, rustfmt, and `bazel test //...`
remain unverified after the last edits. The pinned upstream AuthMgr FE secure
accessor's `addConnection` implementation also remains incomplete, so AuthMgr
acceptance is outstanding; AuthMgr must continue to be described as compiled
and partially integrated, not fully operational. The exact checkpoint and
commands are recorded in `docs/testing-status.md`.

## Future work

ConfirmationUI is intentionally **not implemented**. It requires exclusive, hardware-backed display and input ownership; enabling its upstream app before those contracts exist would not provide a trustworthy confirmation path. Physical-board validation, production root provisioning, and secure display/input remain future board work rather than claims made by the QEMU product.

### Secure confirmation UI

The retained confirmation design gives Trusty temporary exclusive ownership of
a scanout plane and trusted input path, blanks or freezes normal-world
composition, renders a bounded prompt in secure memory, and returns only an
authenticated approval result. A normal-world overlay, ordinary input event,
or merely launching the upstream ConfirmationUI application is insufficient.
No manifest currently requests this service and no test treats it as present.

### Additional upstream secure services

SecretKeeper, protected confirmation, secure clock extensions, identity
credential services, and biometric authenticators remain candidate upstream
Trusty additions. Each requires a concrete BexOS consumer, a typed protocol,
storage and rollback policy, heart-transplant semantics, and board support
before entering the firmware closure. AuthMgr is already included for DICE and
secure-service connection authorization and must not be repurposed as a generic
credential or Gatekeeper-token broker.

### x86-64 secure execution

The integrated QEMU product now uses the in-tree SVM/NPT execution owner and
real BexOS-to-Trusty transport. The requirements below remain applicable to
other secure execution backends and physical products; live Trusty replacement
still needs the implementation and validation described in the checkpoint.


The earlier x86 design is retained as future work. It may host an equivalent
Trusty instance inside a hypervisor-isolated VM or enclave and expose the same
provider-neutral `teed` contract over a hypercall/shared-memory transport.
Simply running the Trusty applications in an ordinary guest does not establish
a secure-world boundary. Any x86 product must define measured launch, isolated
memory, interrupt and DMA ownership, persistent anti-rollback storage, and an
authenticated boot handoff before it can assert the same properties as the
ARM64 TrustZone profile.

### Physical boards and production updates

Production ARM boards remain responsible for authenticated TF-A/BL33 loading,
provisioned AVB roots, lifecycle-controlled device lock state, unique RPMB
authentication keys, cache-coherent shared memory, and a tested reset/recovery
path. A/B boot-slot synchronization and authenticated dynamic Trusty
application updates are future update-engine work. They must preserve the
orchestrator's narrow lifecycle role and cannot bypass the independent
KeyMint, Gatekeeper, AVB, storage, or AuthMgr policies.
