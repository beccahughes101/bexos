# RFC 0008: Storage layers and filesystem capabilities

- Created: 2026-08-26T18:18:51-05:00
- Current implementation: [Implementation and gaps](CURRENT.md)

## Summary

D1 block drivers and userspace filesystems exchange data through FIDL and shared VMOs. Per-process directory capabilities provide storage access without a global filesystem root.

## Design overview

In a capability microkernel, storage is broken into two distinct userspace layers connected by FIDL:

1. **The Block Device Layer (D1 Drivers):** Talks to physical silicon (NVMe, AHCI, SD/eMMC, VirtIO-Blk) and manages zero-copy DMA I/O via shared memory (VMOs).
2. **The Filesystem Layer (Userspace Services):** Consumes block devices and serves hierarchical file/directory capabilities to `appd` and process namespaces.

## The Block Device FIDL Interface (`bexos.storage.block`)

To achieve maximum I/O throughput (NVMe can push gigabytes per second), the block interface must avoid serializing payload bytes across IPC channels. It uses **FIFO request queues referencing shared memory VMOs**.

Implementation lives in `idl/bexos/storage/block.fidl` and is generated by
`//idl:block_fidl_rust`. The checked-in FIDL uses the current BexOS dialect
(`struct Name { ... };` plus `type = strict enum/bits`) while preserving the
same wire concepts from this design. The first D1 NVMe milestone lives under
`drivers/d1/storage/nvmexpress/nvme` and adapts Rust-for-Linux NVMe concepts through the
shared `drivers/d1/support/linux/shim` library.

The BexFS adapter registers transfer VMOs, submits FIFO-style requests, and
translates 512-byte NVMe sectors into bounded 4096-byte roseFS blocks. The GPT
partition view is the only block capability supplied to the filesystem, so a
malformed filesystem cannot address sectors outside its selected partition.

```fidl
library bexos.storage.block;

using bexos.kernel;

type BlockInfo = struct {
    block_size uint32;       // Typically 512 or 4096 bytes
    block_count uint64;      // Total accessible blocks
    max_transfer_blocks uint32;
    flags uint32;            // READ_ONLY, REMOVABLE, TRIM_SUPPORTED
};

type BlockOpcode = strict enum : uint8 {
    READ = 1;
    WRITE = 2;
    FLUSH = 3;
    TRIM = 4;
};

/// Transfer descriptor passed through lock-free shared ring buffer
type BlockRequest = struct {
    req_id uint64;
    opcode BlockOpcode;
    vmo_id uint32;           // ID of the pre-registered shared VMO
    vmo_offset_blocks uint64;// Offset in the buffer
    device_block_offset uint64; // Target LBA on disk
    block_count uint32;      // Number of blocks to transfer
};

type BlockResponse = struct {
    req_id uint64;
    status bexos.kernel.Status;
};

protocol BlockDevice {
    /// Query physical device geometry and sector size
    GetInfo() -> (struct { info BlockInfo });

    /// Register a shared memory VMO for zero-copy DMA transfers
    RegisterBuffer(resource struct {
        vmo handle:VMO
    }) -> (struct {
        status bexos.kernel.Status,
        vmo_id uint32
    });

    /// Unregister a memory buffer
    UnregisterBuffer(struct { vmo_id uint32 }) -> (struct { status bexos.kernel.Status });

    /// Attach a fast FIFO channel for lock-free batch request processing
    GetFifo() -> (resource struct {
        status bexos.kernel.Status,
        fifo_handle handle:CHANNEL
    });
};

```

## The Filesystem FIDL Interface (`bexos.fs`)

This is the protocol consumed by `appd` to construct per-process namespaces (`/pkg`, `/data`, `/tmp`).

Current appd integration constructs `/pkg`, `/data`, `/tmp`, declared
`/shared/<vault_name>` roots, and `/deps/<library>` roots for disk-launched
apps. `/pkg` is read-only package storage from `vfsd.GetPackageDirectory`;
`/data` is package-scoped writable storage from `vfsd.GetUserDataDirectory`;
`/tmp` is a fresh per-launch root brokered through the early D1 MemFS driver;
and `/deps` is populated for declared library dependencies. Shared vault handles
are explicit namespace entries, not ambient paths: appd validates manifest
declarations plus web/local peer trust before requesting
`vfsd.GetSharedVaultDirectory`, and vfsd only provisions the selected backing
directory. Removable-media mounts and document/file-picker grants remain future
namespace entries.

The normative source is `idl/bexos/fs/fs.fidl`, generated by
`//idl:fs_fidl_rust`. It defines filesystem-specific status values, composed
`Node`, `File`, and `Directory` protocols, one-way `Close` and `Open` calls,
and `Filesystem.Mount`. Mount receives a
`bexos.storage.block.BlockDevice` client endpoint, GPT label, options, and a
read-only key VMO. BexFS copies the 256-bit key into a zeroizing wrapper and
does not retain the VMO mapping. A missing or wrong key reports `LOCKED`;
authenticated-data or checksum failure reports `CORRUPT`.

```fidl
library bexos.fs;

using bexos.kernel;

type OpenFlags = strict bits : uint32 {
    RIGHT_READABLE      = 0x00000001;
    RIGHT_WRITABLE      = 0x00000002;
    RIGHT_EXECUTABLE    = 0x00000004;
    CREATE              = 0x00000008;
    TRUNCATE            = 0x00000010;
    DIRECTORY           = 0x00000020;
};

type FileAttributes = struct {
    size_bytes uint64;
    storage_allocated_bytes uint64;
    creation_time_nanos uint64;
    modification_time_nanos uint64;
    mode uint32;
};

protocol Node {
    GetAttr() -> (struct { status bexos.kernel.Status, attr FileAttributes });
    SetAttr(struct { attr FileAttributes }) -> (struct { status bexos.kernel.Status });
    Close();
};

protocol File {
    compose Node;

    /// Streaming read (fallback for small files)
    Read(struct { count uint64 }) -> (struct { status bexos.kernel.Status, data vector<uint8> });

    /// Streaming write
    Write(struct { data vector<uint8> }) -> (struct { status bexos.kernel.Status, written uint64 });

    /// Seek position
    Seek(struct { offset int64, whence uint8 }) -> (struct { status bexos.kernel.Status, new_offset uint64 });

    /// Zero-copy mmap backing: returns a VMO directly mapped to disk cache
    GetBackingMemory() -> (resource struct {
        status bexos.kernel.Status,
        vmo handle:VMO
    });
};

protocol Directory {
    compose Node;

    /// Relative lookup. Traversal above this node via ".." is strictly barred.
    Open(resource struct {
        path string:256,
        flags OpenFlags,
        object server_end:Node
    });

    ReadEntries() -> (struct {
        status bexos.kernel.Status,
        entries vector<DirEntry>
    });

    Unlink(struct { name string:256 }) -> (struct { status bexos.kernel.Status });
};

```

## Filesystem support

Instead of building a single monolithic filesystem to do everything, divide responsibilities across three focused filesystem servers:

| Filesystem | Role in BexOS | Implementation & Strategy |
| --- | --- | --- |
| **`BlobFS` (or MerkleFS)** | **Package Store (`/pkg`)** | **Immutable, Content-Addressed.** Stores `.bexapp` binaries and assets indexed by their Merkle root SHA-256 hash. Provides cryptographic execution integrity and de-duplicates identical packages across apps. |
| **`BexFS`** | **System state and user data** | **roseFS-backed encrypted CoW storage.** The core is pinned to roseFS commit `0cb025fed13db2cd681698bb47f5a77ff6946cbd`; BexOS supplies durable namespace snapshots, GPT isolation, FIDL serving, and key-provider integration. |
| **`MemFS`** | **Ephemeral (`/tmp`)** | **Early D1 in-memory RAM filesystem driver.** Fast, volatile filesystem creating a fresh directory tree per launched process. Discarded when the process closes its tmp handles. |
| **`FAT32` / `Ext4`** | **External USB / Compatibility** | Read/write drivers for external USB drives, FAT32 EFI system partitions, or importing data from legacy disks. |

## Design properties

* **Crash Consistency & Snapshots:** A Copy-on-Write (CoW) filesystem for user data (`BexFS`) guarantees that a sudden power failure or panic leaves zero corrupted inodes.
* **No Path Traversal Attacks:** Because `Directory.Open` is handled relative to the directory capability held by the process, sandboxing is mathematically enforced without global root checks.
* **Live Updates (Heart Transplant):** Because the block driver and filesystems are separated by FIDL channels and shared VMOs, the block storage driver or filesystem server can perform a live userspace upgrade while open file handles remain attached.

## BexFS on-disk and key contract

BexFS uses roseFS container, allocation, keyslot, checksum, and
AES-256-GCM-SIV primitives. Namespace metadata and file data are sealed as
authenticated dual-generation snapshots; the newer valid generation wins on
mount. A successful close or unmount commits the inactive snapshot, updates
the redundant volume headers, and flushes the underlying block device.

Current implementation note: the BexFS core remains no-std and synchronous, but
the deployed D1 filesystem server is now a std-linked Tokio ELF. Tokio owns the
service-loop scheduling and migration quiescence yields; the roseFS/block
storage boundary remains the synchronous `BlockDevice` contract.

`SYS_STATE` contains `/boot_state.bin`, a fixed little-endian `SysStateV1`
record with magic/version, generation, active A/B slot, per-slot tries,
last-known-good slot, last-known-good version, and CRC32C. QEMU uses a declared
deterministic development root. `usersd` recreates user U-KEKs through an
authenticated Trusty KeyMint HMAC operation and transfers them through the
same short-lived key-VMO boundary. Production provisioned roots and physical
RPMB validation remain board-specific work.

## File Systems

BexOS should not expose a global Linux-style VFS root (`/`).

A global root filesystem creates **ambient authority**—where any process can attempt to access /etc/shadow, /dev, or /data by constructing a path string. It also creates shared, mutable global state that complicates capability security, sandboxing, and heart transplant state snapshots.

Instead, BexOS should use a **Capability-Based Per-Process Namespace Model** (similar to Fuchsia's namespaces, Plan 9, and WASI dirfd capabilities).

## How Filesystem Capabilities Work Without a Global Root

In this architecture, filesystems are unprivileged userspace services, and a "path" only exists relative to a capability handle that a process explicitly holds.

## Core Filesystem Architecture

**1\. Filesystems as FIDL Services**
Filesystem implementations (e.g., a native Rust BexFS, a FAT32 driver, or an in-memory MemFS) run as userspace services. They expose a standardized FIDL interface:

Code snippet

* library bexos.fs;
*
* protocol Node {
*     GetAttr() \-\> (struct { attributes FileAttributes });
*     Close();
* };
*
* protocol File {
*     compose Node;
*     Read(struct { count uint64 }) \-\> (struct { data vector\<uint8\> });
*     Write(struct { data vector\<uint8\> }) \-\> (struct { actual uint64 });
*     Seek(struct { offset int64, whence SeekOrigin }) \-\> (struct { new\_offset uint64 });
*     GetBuffer() \-\> (resource struct { buffer handle:VMO }); // Zero-copy mmap
* };
*
* protocol Directory {
*     compose Node;
*     Open(struct {
*         flags OpenFlags,
*         path string,
*         object server\_end:Node
*     });
*     ReadEntries() \-\> (struct { entries vector\<DirEntry\> });
* };

**2\. Assembling Per-Process Namespaces**
When appd launches a process, it builds a local **Namespace Table** (a lightweight routing dictionary) mapping virtual path prefixes directly to channel capabilities:

| Virtual Mount Path | Backing Capability Source | Permissions |
| :---- | :---- | :---- |
| /pkg | Read-only bundle partition handle for this .bexapp | Read / Execute |
| `/deps/<package name>` | Read-only bundle partition handle for this .bexapp | Read / Execute |
| /data | Private encrypted storage directory handle | Read / Write |
| `/shared/<vault name>` | Domain/local shared directory handle (e.g., google\_shared\_vault) | Read / Write (if manifest and peer trust pass) |
| /tmp | Ephemeral MemFS directory handle created on launch | Read / Write |
| /svc | Channel to appd for dynamic FIDL discovery | Connect / Bind |

**3\. Built-In Sandboxing (No Path Traversal Escapes)**
Because path resolution starts from an explicit Directory handle:

* A process executing open("/data/../../etc/passwd") cannot escape /data.
*
* When the filesystem server resolves paths relative to the /data directory handle, attempting to step above the granted root node returns ZX\_ERR\_ACCESS\_DENIED or resolves to /data itself.
*
* There is no /etc, /root, or /sys unless appd explicitly inserts those handles into the process namespace.
*

## How appd Manages Storage

* **Bootstrapping Storage:** During boot, appd connects to the raw storage service (which mounts disk partitions).
*
* **Directory Provisioning:** When an app is installed, appd asks the filesystem service to create a cryptographically isolated directory node (e.g., fs.CreateDirectory("apps/com.monzo:app/data")).
*
* **Sub-Directory Delegation:** When launching com.monzo:app, appd passes only the channel handle representing that specific sub-tree to the child process as /data.
*

## Handling POSIX Compatibility & WASI

* **Embedded POSIX Shims (**libposix **/** musl**):** When legacy C/C++ or Nix runner code calls open("/pkg/assets/logo.png", O\_RDONLY), the userspace shim intercepts the call, finds the matching /pkg channel handle in the process namespace, and sends a Directory.Open("assets/logo.png") FIDL request.
*
* **WASI Compatibility:** WASI natively uses capability-based file descriptors (dirfd). Mapping WASI fd\_read / path\_open onto BexOS directory handles requires near-zero translation overhead.
*
* **Heart Transplants:** Because filesystem state consists of explicit open channel endpoints rather than complex kernel-level VFS lock trees and inode caches, serializing and reconnecting storage handles across a microkernel swap is completely deterministic.

Both choices are solid foundations for bringing up the storage stack in pure Rust, but they have very different integration requirements in a microkernel architecture like BexOS.

## The NVMe Driver (`rust-for-linux/nvme-driver`)

The `rust-for-linux` NVMe driver provides a reference for safe Rust NVMe data structures (Submission/Completion Queue management, doorbells, PRP/SGL descriptors, Admin Commands). However, **it cannot be used as an out-of-the-box drop-in crate** without adapting the host bindings.

### The Linux Kernel Glue Problem

`rust-for-linux` drivers do not target standard `no_std` alone; they depend on the Linux `kernel` crate abstractions (`kernel::pci`, `kernel::dma`, `kernel::sync`, `kernel::page`). In Linux, these types wrap Linux C kernel internals via bindgen.

### How to Port It to BexOS

The adaptation does not require Linux's C code. Decouple the core logic from the Linux kernel crate:
1. **PCI & MMIO Registers:** Replace Linux's `pci::Bar` with a BexOS MMIO VMO handle mapped into the D1 userspace process.
2. **DMA Allocations:** Replace Linux's `dma_alloc_coherent` with kernel contiguous physical VMO allocations.
3. **Queue Submission:** Adapt its `NvmeQueue` and ring buffer structures to consume `bexos.storage.block.BlockRequest` messages directly from the shared memory FIFO.

## The Filesystem (`christhomas/rust-fs-ext4`)

`christhomas/rust-fs-ext4` is a **fantastic fit** for BexOS early bringup:

* **Built for Host-Agnostic FFI / `no_std`:** Unlike Linux in-kernel filesystems, this repository is designed as an isolated pure-Rust ext2/3/4 driver with no host-specific OS assumptions.
* **Clean BlockDevice Trait:** It abstracts disk I/O behind a simple `BlockDevice` trait (`read_block`, `write_block`). In BexOS, implementing that trait means dispatching block reads/writes over the FIDL `BlockDevice` client channel.
* **Full Read/Write + JBD2 Journaling:** It handles crash-safe writes and JBD2 journal replays, making it safe for active OS testing without risking silent filesystem corruption.

## Step-by-Step Bringup Plan

### Phase 1: Mocked ext4 Service in QEMU

* Link `rust-fs-ext4` against an in-memory byte buffer or a simple file-backed BlockDevice trait.
* Implement the `bexos.fs.Directory` and `bexos.fs.File` FIDL endpoints on top of it.
* Verify that the Rust WASM shell can run `ls /data`, `cat /data/test.txt`, and `mkdir /data/my_dir`.

### Phase 2: Extract the NVMe Core Logic

* Strip the `kernel::` crate dependencies from the `rust-for-linux` NVMe driver, keeping the submission/completion queue handlers, admin opcodes, and status bitmasks.
* Bind them to BexOS MMIO address ranges and hardware interrupt events.
* Vendor the Rust-for-Linux reference tree as `third_party/linux_nvme`, pinned
  to the `rnvme-v6.15` lineage. The current QEMU NVMe smoke target attaches an
  emulated NVMe controller, enumerates it through guest-side PCI ECAM config
  space, programs BAR0, and validates a real one-block write/read/compare in
  the kernel. Routing this into the D1 userspace block service remains a
  platform-bus milestone.

### Phase 3: Connect BlockDevice over FIDL

* Implement the `BlockDevice` trait in the ext4 service by routing block I/O requests over the FIDL channel to the NVMe driver service.
